# 外部设计 Review 结果

生成日期：2026-05-08

审查方式：基于 `deployment/frontend/09_external_design_review_prompt.md` 对当前 React 静态 Demo 做纯视觉审查。本轮未安装外部 skill，未执行外部脚本，未修改页面结构、字段合同、指标口径、安全边界或部署架构。

## 1. 总体判断

当前界面整体符合“专业、克制、可信、数据产品感”的方向。它更像健康服务数据治理与运营分析产品，而不是医疗 AI 官网、营销页或炫光大屏。首屏能通过标题、KPI、治理链路和 Demo 边界说明项目价值，也能让需求方理解 React 是静态展示层而非正式系统。色彩、卡片、图表和表格都比较稳，适合截图给需求方做阶段汇报。

## 2. 高优先级问题

没有发现必须阻断部署前检查的视觉问题。

需要关注的点：

- 首屏的 KPI 中“存在费用/支付归属说明”与 Metabase “有客户支付金额记录数”可能被非技术观众误认为同一指标。视觉层面建议后续把标签轻微改为“存在费用/支付归属信息”，但不应改变指标口径或数据。
- 服务记录页在移动端依赖横向滚动查看完整表格，功能可用，但截图汇报时移动端表格不如桌面端清晰。建议演示截图优先使用桌面宽屏。
- 图表页信息密度适中，但 Top 10 横向条形图较多，连续截图时会显得模块重复。可在讲解中强调每张图的运营问题，不需要新增页面或改结构。

## 3. 中低优先级 polish

- KPI 卡片的说明文字已经克制，但“存在费用/支付归属说明”可改为“存在费用/支付归属信息”，更贴近当前计算方式。
- 图表标题准确，均保留“按服务记录统计”或边界说明；后续可在 tooltip 中继续保持“条服务记录”的表达，避免医疗结论化。
- 总览页“模块关系”区块清晰，但视觉上接近流程图摘要，截图时可以和上方“治理链路”一起截，说明会更完整。
- 表格列较多，桌面端可读；移动端可读但主要靠横向滚动。后续 UI polish 可以加强横向滚动提示，但不应减少字段或改变数据合同。
- 详情抽屉克制，字段分组清楚，flags 的解释没有泄露敏感原文。后续可轻微增强 flags 与说明文字的间距，提升扫读感。

## 4. 不应改动的内容

本次视觉审查不建议改动：

- 页面结构。
- 路由结构。
- 页面数量。
- 数据字段。
- JSON 合同。
- 指标口径。
- 敏感字段规则。
- 部署架构。
- 静态 JSON 数据路线。
- 是否接 Supabase。
- 是否引入后端。
- 是否增加线上服务。
- 是否增加登录权限。

## 6. 针对审查重点的结论

- 是否像健康服务数据治理产品：是。
- 是否过度营销化：否。
- 是否医疗 AI 化：否。
- 是否炫光大屏化：否。
- 首屏是否能说明项目价值：能说明 Excel 到结构化数据再到展示层的价值。
- KPI 卡片是否清楚：整体清楚；payment note 标签建议后续轻微改文案。
- 图表标题是否准确：准确，未写成医疗结论。
- 表格是否可读：桌面端可读，移动端可用但更适合横向滚动查看。
- 详情抽屉是否克制：克制，只展示允许字段和 flags。
- 移动端是否可读：基本可读。
- 是否适合截图给需求方看：适合，建议以桌面端截图为主。

## 7. 建议

部署前不需要大改。

后续可选 UI polish：

- 将“存在费用/支付归属说明”轻微改为“存在费用/支付归属信息”。
- 将表格列名“费用/支付归属说明”轻微改为“费用/支付归属信息”。
- 为移动端表格增加横向滚动提示。
- 若部署前要优化性能，可单独处理 ECharts chunk size warning，但不要因此引入后端或改变数据路线。
